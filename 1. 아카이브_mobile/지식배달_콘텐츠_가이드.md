# 지식 배달 콘텐츠 생성 가이드 (매일 생성용)

> 직장인/수험생 배달 콘텐츠를 **어디에 · 어떤 형식으로 · 어떤 id로** 추가하는지의 단일 기준 문서.
> 매일 조금씩 생성할 때 아래 §4의 "복붙 프롬프트"를 다른 대화에 붙여넣고 주제만 바꾼다.
> **기준일 2026-06-24** — 아래 "다음 id"는 이 날짜 기준. 새 작업 전 `npm run scan-ids`로 항상 재확인.

---

## 1. 저장 위치 (3개 폴더)

| 모드 | 폴더 | 적재 키 |
|---|---|---|
| **직장인** | `public/data/knowledge_db/*.json` | english_theme_packs · english_expressions · chinese_expressions · history_facts |
| **직장인 (신규)** | `public/data/work_db/*.json` | classic_quotes(고전) · idiom_cards(고사성어) · daily_insights(인사이트) |
| **수험생** | `public/data/exam_db/*.json` | exam_vocab_themes · exam_history_items |

- 서버가 폴더 전체 `.json`을 읽어 메모리/SQLite에 적재(중복 id는 자동 스킵). 배달은 AI 호출 없이 회전 서빙.
- `archive.db` · `dailyFeeds.json` 은 **런타임 생성물 — 직접 편집 금지.** 콘텐츠는 항상 위 시드 폴더에만.
- **모드 격리:** 수험생 배달은 `exam_db`만 읽는다. `knowledge_db`·`work_db`(직장인)는 수험생에 **절대 안 뜸**. 직장인 콘텐츠를 `exam_db`에 넣지 말 것(그 반대도).

> ⚠️ 폐기됨(더 넣지 말 것): 옛 `idioms_and_quotes`(IQ_) / `quote_daily`(명언) — 고사성어는 이제 `work_db/idiom_cards`로, 명언은 고전(LIBER)·인사이트로 대체됨.

> 📦 **배달 피드는 3개다**(2026-09-13~): 영어(en_expr) · 미국 시황(us_market) · **지식 한줌(daily_knowledge)**.
> 지식 한줌은 역사 → 고사성어 → 인사이트 → 고전을 **하루에 한 갈래씩** 돌려 배달한다(날짜 기반 4일 주기).
> 네 가지 콘텐츠는 전부 그대로 쓰이며 생성 방법도 아래 블록 그대로다 — 다만 한 갈래가 4일에 한 번만 나오므로 **항목 하나의 밀도**가 중요해졌다.

## 2. 절대 규칙
1. **최상위 키 이름 정확히** (오타 시 미적재).
2. **id 전역 고유** — 이미 쓴 번호 재사용 금지(`INSERT OR IGNORE`라 조용히 누락). 항상 "다음 id"부터.
3. **파일 이름 자유** (폴더 전체를 읽음). 관례: knowledge_db=`batch_NN_주제.json`, work_db=`<타입>_NN.json`, exam_db=`vocab_NN_csat.json`/`history_NN_kr.json`.
4. work_db 항목은 `targetMode: "work"`, `used: false` 고정.
5. JSON에 `meta`(작성일·주제 메모)는 넣어도 무시됨 — 자유롭게.
6. **같은 표현을 다시 넣지 말 것** — 중복 배달 방지는 `item_id`로만 판단해서, 같은 표현이
   다른 id로 여러 개 있으면 60일 안에 여러 번 배달돼도 시스템이 눈치채지 못한다.
   (2026-09: 평면 풀 588개 중 119개가 중복이었고 `think outside the box`는 8번 들어 있었다)
7. **`theme_category`는 `business_meeting`/`daily_travel`/`drama_spoken` 셋 중 하나만.**
   `level`은 `beginner`/`intermediate`/`advanced` 셋 중 하나만. 목록에 없는 값을 쓰면
   어떤 설정으로도 매칭되지 않아 콘텐츠가 통째로 죽는다(부팅 로그에 경고가 뜬다).

### (D) 직장인 — 영어 테마팩  → `knowledge_db/batch_NN_*.json`
```
SJ 아카이브 직장인 배달 "영어 테마팩"을 생성한다. JSON 한 덩어리만 출력, 설명 금지.
- 위치: public/data/knowledge_db/ 의 .json, 최상위 키 "english_theme_packs"
- id: PACK_EN_<다음 번호>부터(현재 다음 PACK_EN_028), 표현 id "<팩id>_01"…"_05". 전역 고유.
- 한 팩 = 실전 상황 테마 1개 + 표현 5개 + 마스터 단락. dialogue 3~4턴(\n 줄바꿈, 객체 `{"A":"...","B":"..."}` 형태 금지 — 문자열로), nuance는 "왜 이 표현"을 2~4문장.
- `example_ko`(예문 한국어 해석) 필수 — Example 섹션 길이 문제로 dialogue 전체는 번역 안 하고 예문 한 줄만 번역해서 붙인다(07-26 결정).
- **`theme_category` 필수(07-27 결정)** — 관리 화면 "집중 테마" 체크박스와 실제로 매칭되는 값이어야 배달에 반영됨. 반드시 다음 3개 중 하나:
  - `business_meeting` — 비즈니스 영어 전반(회의·이메일·협상·리더십·면접 등 직장 상황 통칭. 지금까지 만든 팩 대부분이 여기 — 07-27 기준 40개 중 37개)
  - `daily_travel` — 일상/여행 회화(07-27 기준 1개뿐 — 우선적으로 채워야 할 카테고리)
  - `drama_spoken` — 미드 구어체(07-27 기준 1개뿐 — 마찬가지로 우선 채워야 함)
  - (예전에 쓰던 `office_email`은 폐기 — business_meeting에 흡수됨. 새 콘텐츠에 쓰지 말 것)
- **`level`은 이제 3단계**: `beginner`(초급) / `intermediate`(중급) / `advanced`(고급). **같은 theme_category 안에서 레벨별로 짝을 맞춰 작성하는 게 원칙** — 어려운 단어로 바꾸는 게 아니라 "같은 실제 상황을 원어민이 얼마나 압축해서 말하는가"의 차이로 레벨을 가른다.
  예: 배를 탈 때 → 초급 "I want to **take a boat**." / 고급 "We're **boarding** at 9 AM." (같은 상황, board를 동사로 바로 쓰는 게 더 원어민스러움)
  → 새 테마팩을 만들 때는 가능하면 같은 theme_category에서 다른 level 팩도 같이(또는 다음 배치에) 만들어서, 그 카테고리를 어느 레벨로 골라도 팩이 있게 할 것. 특히 daily_travel·drama_spoken은 beginner가, business_meeting은 상대적으로 advanced가 부족하니 그쪽부터 채울 것.
- 주제: <여기에. 예: "재택·하이브리드 근무 커뮤니케이션">
스키마:
{ "meta":{"topic":"...","created":"YYYY-MM-DD"},
  "english_theme_packs":[ {"id":"PACK_EN_###","theme_key":"snake_case","theme_category":"business_meeting|daily_travel|drama_spoken","theme_title":"한국어 제목","theme_title_en":"English Title","level":"beginner|intermediate|advanced","delivery_date":null,
    "expressions":[ {"id":"PACK_EN_###_01","order":1,"expression":"...","meaning":"...","nuance":"...","dialogue":"A: ...\nB: ...","example":"...","example_ko":"예문 한국어 번역","practice":"..."} ],
    "master_paragraph":{"text":"5~7문장 영어","translation":"한국어 번역","highlights":["표현1","표현2"]} } ] }
```
> 영어 평면 표현(`english_expressions`, 다음 EN_326)·중국어(`chinese_expressions`, 다음 ZH_078)는 기존 batch 파일 스키마를 그대로 따른다. 이 평면 풀은 아직 theme_category 태깅 전이라(레벨만 필터링됨) 테마팩이 항상 우선 — 평면 풀은 테마팩 개수가 설정값보다 부족할 때 보충용으로만 쓰인다.

## 4-B. 평면 영어 풀 뉘앙스 백필 (진행 중 · 차차)

> **왜:** 테마팩(225개)에는 `nuance`가 100% 있는데 평면 풀에는 0%였다.
> 설정한 테마·레벨에 맞는 팩이 없으면 Tier 2(평면 풀)로 떨어지는데, 이때 사용자는
> **뉘앙스 없는 얇은 카드**를 받고 왜 얇아졌는지 알 수 없다.
> 뉘앙스가 "이해"를 만드는 칸이므로 이걸 채우는 것이 영어 콘텐츠 최대 과제다.

### 진행 상황

| | 개수 |
|---|---:|
| 평면 풀 전체 | **469** (중복 119개 제거 후) |
| 뉘앙스 있음 | 58 (`batch_15_mideu_en` 29 + `batch_16_everyday_en` 29) |
| **남은 것** | **411** |

### 순서 (트래픽 많은 것부터)

테마팩이 `business_meeting` 38 / `daily_travel` 4 / `drama_spoken` 3으로 쏠려 있어서,
**일상·여행·미드로 설정한 사용자는 거의 항상 평면 풀로 떨어진다.** 그래서 그쪽 파일이 우선이다.

```
✅ batch_15_mideu_en      (29)  미드 구어체 — 완료
✅ batch_16_everyday_en   (29)  일상 — 완료
   batch_14_reallife_en   (29)  실생활   ← 다음
   batch_02_daily_life    (79)  일상 — 가장 큼
   batch_01_business      (39)  비즈니스
   나머지 mixed/workplace 계열
```

> 평면 풀에는 `example_ko`(예문 한국어)도 없다. 뉴앙스를 채울 때 같이 넣으면
> 두 번 읽지 않아도 된다.

### 작성 기준

- **뜻풀이(`meaning`)와 겹치지 않게 쓴다.** 뜻은 이미 위 칸에 있다.
- 담을 것: **언제 쓰면 안 되는지 / 비슷한 표현과 뭐가 다른지 / 한국인이 어디서 틀리는지.**
- 구어·미드 표현은 **톤과 관계가 뜻을 바꾼다** — 억양에 따라 의미가 갈리면 반드시 적는다.
- 분량 **120~180자**. 테마팩 평균이 165자이므로 그 언저리면 자연스럽다.
- 어원·출처는 정확할 때만(예: Touché는 펜싱 프랑스어, "You had me at hello"는 제리 맥과이어).
  확실하지 않으면 쓰지 않는다.

### 작성 프롬프트
```
SJ 아카이브 평면 영어 표현에 'nuance' 필드를 채운다. JSON 한 덩어리만 출력.
- 대상 파일: public/data/knowledge_db/<파일명>의 english_expressions
- 출력 형식: { "EN_###": "뉘앙스 문장", ... } — id를 키로 하는 객체 하나
- 각 뉘앙스는 120~180자. meaning과 내용이 겹치면 안 된다.
- 반드시 담을 것: 언제 쓰면 안 되는지 / 비슷한 표현과의 차이 / 톤에 따른 의미 변화
- 확실하지 않은 어원·출처는 쓰지 않는다.
```

> ⚠️ 평면 풀은 **SQLite가 아니라 JSON에서 직접 읽는다**(`loadKnowledgeDB()`가 모듈 캐시).
> 그래서 마이그레이션 없이 파일만 고치면 되지만, **서버 재시작(=배포) 전까지는 반영되지 않는다.**

## 4-C. 영어 단어 트랙 (english_words)

> **표현(english_expressions)과 별개 트랙.** 기존 813개 중 단어는 3%뿐이라 어휘 확장 기능이
> 사실상 없었다. 2026-09-20에 신설.

### 왜 별도 피드가 아닌가
배달 피드를 6개 → 3개로 줄인 방향을 되돌리지 않기 위해, **영어 카드 하단 섹션**으로 넣는다.
`wordEntries` 배열이 영어 피드에 실려 오고 `Mob._renderWordTrack()`이 그린다.
Tier 1(테마팩)·Tier 2(평면 풀) **양쪽 경로 모두**에 붙어 있어야 한다 — 한쪽만 붙이면
평면 풀로 떨어진 사용자만 단어를 못 받는다.

### 핵심: 단어는 뜻만으론 못 쓴다
`collocations`(어떤 말과 붙는가)와 `confusable`(헷갈리는 단어와 뭐가 다른가)이 이 트랙의 존재 이유다.
이 두 칸이 비면 그냥 단어장이 되고, 사전보다 나을 게 없어진다.

### 생성 프롬프트
```
SJ 아카이브 직장인 배달 "영어 단어"를 생성한다. JSON 한 덩어리만 출력, 설명 금지.
- 위치: public/data/knowledge_db/ 의 .json, 최상위 키 "english_words"
- id: WD_<다음 번호>부터 전역 고유(현재 다음 WD_021). 단어 10~20개.
- 주제: <여기에. 예: "회의·보고에서 자주 쓰는 동사">
- **기존 표현 풀과 겹치지 않게 할 것** — 이미 english_expressions에 있는 단어는 피한다.
- collocations는 실제로 자주 붙는 3개. 사전식 나열이 아니라 통째로 외워 쓸 덩어리로.
- confusable은 **비슷해서 틀리는 단어**와의 차이를 구체적으로. 없으면 이 단어를 고르지 말 것.
- nuance는 언제/왜 쓰는지, 한국인이 어디서 틀리는지. 120~180자.
- level은 beginner|intermediate|advanced 중 하나.
스키마:
{ "meta":{"topic":"...","created":"YYYY-MM-DD"},
  "english_words":[ {"id":"WD_###","word":"streamline","pos":"동사","meaning":"뜻 한 줄",
    "level":"intermediate","collocations":["...","...","..."],
    "confusable":"비슷한 단어와의 차이 2~3문장","nuance":"쓰임 120~180자",
    "example":"영어 예문","example_ko":"한국어 번역"} ] }
```

## 5. 추가 후 체크리스트
```
□ 올바른 폴더인가? (직장인=knowledge_db/work_db, 수험생=exam_db)
□ 최상위 키 정확? (오타 시 미적재)
□ id가 "다음 id"부터 시작하고 기존과 안 겹치는가? (npm run scan-ids 로 확인)
□ JSON 문법 OK? (node -e "require('./파일.json')")
□ work_db 항목에 targetMode:"work", used:false 들어갔는가?
□ 서버 재시작 후 콘솔 로그로 적재 확인:
   [WorkDB] 로드 CLQ:.. IDC:.. INS:..  /  [EnTheme Seed] ..  /  [ExamKnowledge Seed] ..
```

> **다음 id 재확인:** `cd "1. 아카이브_mobile" && npm run scan-ids`
> **자동 일괄 생성(선택):** `node scripts/buildWorkContent.js all`(파일럿) / `... all --full`(전체) — Claude 기본, work_db로 출력.

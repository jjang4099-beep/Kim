## 1. 왜 안 쌓이는가 — 확인된 원인

### ★ 사진은 공유 시트로 앱에 보낼 수 없다

`manifest.json`의 share_target:

```json
"share_target": {
  "action": "/share-handler",
  "method": "GET",
  "enctype": "application/x-www-form-urlencoded",
  "params": { "title": "title", "text": "text", "url": "url" }
}
```

`files`가 없고 `method`가 GET이다. Web Share Target으로 **파일을 받으려면
반드시 `POST` + `multipart/form-data` + `params.files`** 여야 한다.

즉 지금은 **링크·텍스트만** 공유할 수 있고, 사진을 남기려면
앱을 열고 → 추가 모달 → 라이프 기록 → 사진 선택 → 저장을 거쳐야 한다.
사진첩에서 "공유 → 아카이브" 한 번으로 끝나지 않는다.

이게 라이프 기록이 3개월에 3건인 가장 큰 이유로 보인다.

### 글이 비는 이유

사진을 올리는 순간에는 쓸 말이 없고, 쓸 말이 생겼을 때는 앱을 안 연다.
`text`가 0자인 기록이 이미 나온 것이 그 증거다.
**사용자가 "사진이나 그때 적은 글이 중요하다"고 했는데, 그 글이 지금 안 남고 있다.**

## 2. 설계 원칙

> **기록을 시키지 말고, 이미 하는 행동에서 주워담는다.**

그 공유 한 번에 올라타는 것이 이 계획의 전부다.

## Phase A — 사진 공유가 실제로 되게 ✅ 완료 (2026-09-13)

### A-1. share_target에 files 추가
```json
"share_target": {
  "action": "/share-handler",
  "method": "POST",
  "enctype": "multipart/form-data",
  "params": {
    "title": "title", "text": "text", "url": "url",
    "files": [{ "name": "photos", "accept": ["image/*"] }]
  }
}
```

### A-2. 서비스워커가 POST 공유를 처리
`sw.js`의 `handleShareTarget`은 현재 GET 쿼리스트링만 읽는다.
`request.formData()`로 파일을 꺼내 `POST /api/items/life`로 넘기도록 분기를 추가한다.

> ⚠️ GET 분기(링크 공유)를 그대로 둔 채 POST 분기를 **추가**한다. 기존 링크 공유가 깨지면 안 된다.
> ⚠️ `CACHE_NAME`을 반드시 올린다. SW가 안 바뀌면 이 기능이 통째로 적용되지 않는다.

### A-3. 공유 직후 "한 줄 남기기"
사진이 저장된 뒤 **가벼운 한 줄 입력 화면**을 띄운다. 건너뛰기도 한 번에 되게 한다.
여기가 이 앱의 핵심 자산(그날의 글)이 생기는 유일한 지점이다.

- 기본값: 오늘 날짜, 기분 미선택
- 입력 없이 닫아도 사진은 이미 저장돼 있다(기록 유실 금지)

### A-4. 서버 폴백 (계획에 없었으나 추가)
SW가 설치 전이거나 갱신 중이면 POST가 서버로 그대로 넘어온다.
라우트가 없으면 404 → **공유한 사진이 통째로 사라진다.**
`app.post('/share-handler')`를 추가해 같은 동작을 하게 했다.
페이지 이동이라 401 JSON 대신 앱으로 리다이렉트해야 해서
`lib/auth.js`에 `getUserId(req)`(토큰 있으면 userId, 없으면 null)를 추가했다.

### 완료 조건
- [x] 여러 장을 한 번에 공유해도 한 기록으로 묶인다 (2장 → 기록 1건 확인)
- [x] 기존 링크·텍스트 공유가 그대로 동작한다 (SW 경로·서버 폴백 양쪽 확인)
- [x] 공유 직후 한 줄을 남기면 같은 기록에 붙는다 (사진 2장 유지 + 제목 동기화)
- [x] SW 경로와 서버 폴백 경로 둘 다 동작한다
- [ ] **안드로이드 실기기에서 사진첩 → 공유 → 아카이브** ← 배포 후 사용자 확인 필요

> 실기기 확인이 남아 있다. 로컬에서는 OS 공유 시트를 띄울 수 없어
> `/share-handler`로 직접 multipart POST를 보내 양쪽 경로를 검증했다.

> iOS 사파리는 Web Share Target을 지원하지 않는다. iOS는 앱 내 업로드가 계속 주 경로다.
> 이 제약은 문서에 남기고, iOS 대응은 나중에 따로 판단한다.

## Phase A+ — 모드 시기 기록 ✅ 완료 (2026-09-13)

> **수험생 시절을 일반인이 된 뒤에도 자산으로 남기기 위한 토대.**
> 소급이 불가능한 기록이라 다른 무엇보다 먼저 깔았다.

### 프레이밍
**모드는 "지금 무엇을 하는가"(작업 공간)이고, 연대기는 "무엇을 해왔는가"(생애)다.**
격리해야 하는 것은 작업 공간이고, 생애는 격리하면 안 된다.
연대기는 이미 `mode` 파라미터 없이 전체를 조회하므로(`chronicle.js`) 접점이 이미 있었다.
모드 전환도 데이터를 지우는 게 아니라 `items.mode`로 남아 있을 뿐이다.

### 한 것
- `user_mode_periods` 테이블 신설 — 이벤트 로그가 아니라 **구간 모델**.
  연대기에 필요한 건 "3월 12일에 바꿨다"가 아니라 "2024.03 ~ 2027.02 수험생"이라는 띠이기 때문.
- `UsersDB.recordModeChange()` — **멱등**. 앱을 열 때마다 `setMode`가 불리므로
  여기서 막지 않으면 같은 구간이 수십 개로 쪼개진다.
- `GET /api/auth/mode-periods` — 연대기 띠 + 졸업 결산의 기간 근거
- **클라이언트가 `PATCH /api/auth/mode`를 아예 호출하지 않고 있었다.**
  라우트만 있고 죽어 있어서 `users.current_mode`가 가입 기본값에 멈춰 있었음 — 같이 고침.
- 기존 유저 백필: 과거 전환 이력은 복원 불가이므로 **추측하지 않고**
  "가입 시점부터 현재 모드로 쭉" 한 구간만 연다.

### 완료 조건
- [x] 모드를 바꾸면 이전 구간이 닫히고 새 구간이 열린다
- [x] 같은 모드로 여러 번 호출해도 구간이 쪼개지지 않는다 (`periodStarted: false`)
- [x] 앱 재접속 2회에도 구간 수가 그대로다
- [x] 기존 유저에게 첫 구간이 자동으로 생긴다 (4명 시드 확인)

## Phase C0 — 수험생 기록을 연대기에 연결 (다음)

Phase A+ 위에 올라가는 것들. 순서대로.

1. **연대기에 시기 띠** — `mode-periods`를 타임라인 위에 깔고 구간 라벨 표시
2. **수험생 기록은 월 단위로 축약** ⚠️ 중요
   낱개 오답 사진이 연대기에 그대로 뜨면 문제집 사진 수백 장이 추억을 덮는다.
   `3월 — 수학 오답 12개, 지수함수를 3번 다시 봤다` 형태로 뭉쳐서 한 줄.
   **사진과 글은 낱개로, 오답은 집계로** — 같은 타임라인이지만 입자가 다르다.
3. **졸업 결산** — 모드를 영구 전환할 때 수험생 시절 결산을 자동 생성해
   연대기에 항목 하나로 박는다. 삭제가 아니라 봉인이자 승격.
   오답노트 Phase 2(`unitCode`)가 끝나야 *"지수함수에서 47번 틀렸고 결국 넘어갔다"*가 나온다.
4. **"그때의 나" 회상** — 일반인 모드 홈에 수험생 시절 항목이 가끔 뜬다.
   **읽기 전용**(저장·편집·복습 불가) — 모드 격리 규칙을 지키면서 연결하는 방법.
5. **모의고사 기록** — 현재 기능이 **아예 없다**(`모의고사`/`mock_exam` grep 0건).
   오답 개수보다 성적 추이가 "치열했다"를 훨씬 잘 증명하므로 졸업 결산의 주인공감.
   날짜 + 과목별 등급/점수만 받으면 되니 비용도 싸다.

> 가입 화면 문구도 "수험생 / 일반인"이 아니라 **"지금 수험생인가요?"**가 맞다.
> 영구 정체성이 아니라 현재 상태를 묻는 것이라야 전환이 자연스럽다.

## Phase C — 연대기 보강

연대기(`chronicle.html`)는 이미 동작한다. 데이터가 쌓인 뒤 손볼 것만 적어둔다.

- **월별 파노라마 뷰**: 지금은 날짜 스트립 + 하루 펼침. 연말용으로 *한 해를 한 화면에* 훑는 모드 추가
- 사진이 있는 날을 시각적으로 더 강하게(표제일 `記` 이미 있음)
- 그날의 글을 사진 위 캡션처럼 배치

> ⚠️ **가로 날짜 스트립 + 아래 펼침 구조를 2단 레이아웃으로 되돌리지 말 것.** 확정된 방향이다.

## Phase D — 연말 공유 카드 (인스타그램)

### D-1. 현실 확인
인스타그램에 **자동으로 올려주는 것은 불가능하다.** Graph API는 비즈니스/크리에이터 계정 +
앱 심사가 필요하고 개인 계정 자동 게시는 열려 있지 않다.

현실적인 경로는 두 가지다.
1. **`navigator.share({ files })`** — 모바일에서 OS 공유 시트를 띄우면 인스타가 목록에 뜬다. **이게 주 경로.**
2. 이미지 다운로드 → 사용자가 직접 올림 (데스크톱 폴백)

### D-2. 카드 생성 방식
**클라이언트 Canvas**로 그린다. 서버 이미지 라이브러리(sharp 등)는 alpine에서 네이티브 의존성이 번거롭고,
사진이 같은 오리진이라 canvas가 오염되지 않으므로 브라우저에서 그리는 편이 간단하고 안전하다.

- 규격: 1080×1350(피드 4:5) / 1080×1920(스토리) 두 종
- 폰트는 로드 완료(`document.fonts.ready`) 후 그린다 — 안 그러면 글자가 빠진다
- `canvas.toBlob()` → `navigator.share({ files: [file] })`, 미지원이면 다운로드 폴백

### D-3. 카드 종류 (연말 Wrapped)
데이터가 실제로 받쳐주는 것만 만든다. 숫자가 초라하면 숫자를 크게 쓰지 않는다.

| 카드 | 내용 |
|---|---|
| 표지 | `2026년의 나` + 대표 사진 1장 |
| 사진 모자이크 | 그 해 사진 9~12장 그리드 |
| 그날의 한 줄 | 내가 쓴 글 중 3~4개 발췌 |
| 배운 것 | 저장한 지식 중 도메인 분포 + 대표 3개 |
| 총평 | 기존 `/api/summary/yearly/:year` AI 총평에서 2~3문장 |

### 완료 조건
- [ ] 모바일에서 공유 시트가 뜨고 인스타가 목록에 보인다
- [ ] 글자가 잘리거나 빠지지 않는다(폰트 로드 대기)
- [ ] 사진이 없는 해를 골라도 카드가 깨지지 않는다
- [ ] 데스크톱에서 다운로드 폴백이 동작한다

## 작업 순서 요약

```
Phase A   사진 공유 경로 뚫기   → 완료 ✅
Phase A+  모드 시기 기록        → 완료 ✅ (소급 불가라 먼저 깔았다)

```

**Phase A가 전부다.** 지금 연대기를 아무리 예쁘게 만들어도 넣을 것이 3건뿐이다.

## 하지 말 것

- 연대기 레이아웃을 2단으로 되돌리기 (확정된 방향)
- 인스타 자동 게시 기능 약속하기 (API가 허용하지 않는다)
- 공유 직후 입력을 **필수**로 만들기 — 건너뛰기가 안 되면 공유 자체를 안 하게 된다
- 사진을 `public/uploads/`에 저장하기 — 반드시 `_DATA_DIR`(Fly 영구 볼륨). 예전에 이것 때문에
  재배포마다 사진이 전부 날아갔고, 그때 올린 사진은 복구 불가다
- `sw.js` 고치고 `CACHE_NAME` 안 올리기 — 적용 자체가 안 된다

## 열린 질문

- **iOS**: Web Share Target 미지원. 사용자 비중을 보고 대응 여부를 정한다.
- **사진 용량**: 영구 볼륨 용량과 비용. 원본을 그대로 둘지, 리사이즈해 저장할지.
- **공개 범위**: `life.privacy` 필드가 이미 있으나 쓰이지 않는다. 공유 카드에 어디까지 넣을지와 연결된 문제.
